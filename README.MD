# Cosmetic Inventory System - система учёта косметики

Учебное приложение на Python и Django для учёта косметических средств,
контроля запасов и сроков годности. Доступ веб-интерфейса к данным реализован
через Django ORM.

## 1. Назначение проекта

Cosmetic Inventory System предназначена для хранения сведений о косметических средствах и работы с ними.

Приложение позволяет:

- просматривать список косметических средств;
- открывать подробную информацию о выбранном средстве;
- контролировать количество косметики;
- отслеживать сроки годности;
- определять средства, требующие пополнения или замены;
- искать средства по названию, бренду или категории;
- фильтровать средства по категории;
- сортировать средства по сроку годности, названию или количеству;
- просматривать каталог постранично с сохранением параметров поиска;
- создавать, редактировать и удалять средства через веб-формы;
- загружать и отображать изображения косметических средств;
- просматривать сводную статистику;
- хранить данные между запусками приложения.

Проект развивается поэтапно: консольная версия приложения сохранена, а веб-интерфейс постепенно переводится на возможности Django.

## 3. Предметная область

В Django ORM предметная область представлена моделями `Product`, `Brand` и
`Category` из `products/models.py`.

Объект `Product` содержит:

- `id` - уникальный идентификатор;
- `name` - название средства;
- `brand` - внешний ключ на `Brand`;
- `category` - внешний ключ на `Category`;
- `quantity` - количество единиц;
- `expiry_date` - срок годности;
- `image` - необязательное изображение средства из каталога медиафайлов;
- `slug` - уникальный читаемый идентификатор в URL;
- `low_stock` - вычисляемый базой данных признак низкого остатка.

Объект `Brand` представляет бренд косметики и содержит поля:

- `id` - уникальный идентификатор;
- `name` - уникальное название бренда.

Объект `Category` представляет категорию косметического средства и содержит
поля:

- `id` - уникальный идентификатор;
- `name` - уникальное название категории.

Каждый бренд и каждая категория могут относиться к нескольким средствам. Связи
настроены через `ForeignKey` с `on_delete=models.PROTECT` и
`related_name="products"`. Удалить используемый бренд или категорию нельзя.

Модель `Product` поддерживает изменение количества, определение состояния
запасов и срока годности. Для количества используется `PositiveIntegerField` и
ограничение `quantity >= 0`, а дата хранится в `DateField`.

Рабочие данные Django хранятся в `db.sqlite3`, структура которой управляется
миграциями. База ПР7 `data/cosmetic_inventory.sqlite` сохранена без изменений и
используется как источник для повторяемого переноса данных в ORM.

## 5. Веб-интерфейс

Веб-часть приложения реализована на Django.

Основные страницы:

- `/` - главная страница;
- `/products/` - список косметических средств;
- `/products/?q=<запрос>` - поиск по названию, бренду или категории;
- `/products/?category=<категория>` - фильтрация по категории;
- `/products/?sort=<режим>` - сортировка по сроку, названию или количеству;
- `/products/?page=<номер>` - постраничный вывод каталога;
- `/products/create/` - создание косметического средства;
- `/products/attention/` - средства с низким остатком или близким сроком годности;
- `/products/statistics/` - сводная статистика по категориям и брендам;
- `/products/<slug>/` - подробная информация о средстве по читаемому адресу;
- `/products/<slug>/edit/` - редактирование существующего средства;
- `/products/<slug>/delete/` - подтверждение и удаление средства;
- `/products/<unknown_slug>/` - страница отсутствующего средства с кодом 404;
- `/media/products/<имя_файла>` - загруженное изображение при локальной
  разработке;
- `/admin/` - административный интерфейс Django;
- `/__debug__/` - служебные маршруты Debug Toolbar при `DEBUG = True`;
- неизвестный адрес - общая страница ошибки 404 при `DEBUG = False`.

Для формирования страниц используются Django-шаблоны. Генерация HTML непосредственно в Python-коде веб-представлений не применяется, функция `page()` удалена.

View-функции получают объекты через Django ORM, вычисляют необходимые статусы и
передают данные в шаблоны через контекст. Бренды и категории загружаются вместе
со средствами через `select_related()`, что исключает отдельные запросы для
каждого связанного объекта.

В текущем веб-интерфейсе доступны список и карточка средства, поиск,
фильтрация, сортировка, пагинация, контроль средств, требующих внимания,
статистика, а также создание, редактирование и удаление записей. При
переключении страниц сохраняются параметры поиска, категории и сортировки.
Изменяющие операции выполняются через Django Forms и ORM; административный
интерфейс остаётся дополнительным способом управления данными.

### Формы Django

Практическая работа №11 посвящена теме «Формы в Django». Её цель в проекте -
реализовать получение, проверку и сохранение пользовательских данных через
`Form` и `ModelForm`, не нарушая существующую архитектуру, маршрутизацию и
правила предметной области. Классы форм находятся в `products/forms.py` и
адаптируют задания методических указаний к учёту косметики.

`ProductFilterForm` наследуется от `forms.Form`, потому что фильтрация не
создаёт и не изменяет объект модели. Форма получает параметры `request.GET`,
проверяет поисковую строку, категорию и режим сортировки методом `is_valid()`,
после чего представление использует только значения из `cleaned_data`.
Параметры фильтрации остаются в адресной строке и сохраняются при переходе
между страницами каталога.

`ProductForm` наследуется от `forms.ModelForm` и связан с моделью `Product`.
В `Meta.fields` явно разрешены только поля `name`, `brand`, `category`,
`quantity`, `expiry_date` и `image`; служебные поля `slug` и `low_stock`
пользователь изменять не может. Для полей настроены подписи модели, подсказки,
виджеты HTML5 и CSS-классы Bootstrap.

Одна форма используется для двух сценариев:

- при GET-запросе страницы создания отображается несвязанная пустая форма;
- при POST-запросе форма связывается с `request.POST` и `request.FILES`,
  проверяется и сохраняет новое средство после успешной валидации;
- при редактировании в `ProductForm` передаётся `instance=product`, поэтому
  изменяется существующая запись, а не создаётся новая;
- введённые значения и сообщения об ошибках сохраняются при повторном выводе
  невалидной связанной формы.

Метод `clean_expiry_date()` запрещает сохранять срок годности в прошлом и
возвращает понятное сообщение через `ValidationError`. Количество проверяется
типом поля модели, ограничением базы данных и атрибутом `min` виджета. Для
изображений разрешены JPEG, PNG и WebP размером не более 5 МБ; дополнительно
выполняется проверка содержимого средствами `ImageField` и Pillow.

Все POST-формы содержат `{% csrf_token %}`. Удаление не выполняется GET-запросом:
сначала пользователь открывает страницу подтверждения, а изменение базы данных
происходит только после POST. Отсутствующие объекты редактирования и удаления
обрабатываются через `get_object_or_404()`.

Форма загрузки использует `enctype="multipart/form-data"`, а представления
передают в неё `request.FILES`. Изображения сохраняются в `media/products/`,
отображаются на подробной странице средства и не добавляются в Git. Настройки
`MEDIA_ROOT` и `MEDIA_URL` находятся в `cosmetic_inventory/settings.py`;
обслуживание `/media/` из Django предназначено только для локального режима
`DEBUG`.

### Административный интерфейс

Модели `Product`, `Brand` и `Category` зарегистрированы в Django Admin. Список
средств поддерживает поиск по названию, бренду и категории, фильтрацию,
сортировку, постраничный вывод и редактирование количества. Поля `slug` и
`low_stock` доступны только для чтения. Групповое действие пополняет выбранные
позиции до двух единиц, а связанные средства выводятся внутри страниц бренда и
категории.

## 6. Django Template Language

Шаблоны используют возможности Django Template Language.

### Базовый шаблон

Общая HTML-структура страниц находится в:

```text
templates/base.html
```

Базовый шаблон подключает Bootstrap, собственные статические файлы, навигацию и содержит блоки для заголовка и основного содержимого:

```django
{% block title %}{% endblock %}
{% block content %}{% endblock %}
```

Дочерние шаблоны наследуют его:

```django
{% extends "base.html" %}
```

### Включаемые шаблоны

Повторяющиеся фрагменты вынесены в отдельные файлы:

- `templates/includes/navigation.html` - общая навигация;
- `templates/products/includes/product_card.html` - карточка средства в списке.

Они подключаются тегом `include`:

```django
{% include "includes/navigation.html" %}
{% include "products/includes/product_card.html" with product=item.product needs_attention=item.needs_attention only %}
```

### Контекст

Представления передают данные в шаблоны через словарь контекста. Например, страница списка получает заголовок и подготовленную коллекцию средств:

```python
context = {
    "page_title": "Косметические средства",
    "product_items": product_items,
    "page_obj": page_obj,
}
```

В шаблонах значения доступны по именам переменных:

```django
{{ page_title }}
{{ product.name }}
```

### Циклы и условия

Список средств формируется циклом:

```django
{% for item in product_items %}
{% empty %}
{% endfor %}
```

Тег `empty` обеспечивает отдельное отображение пустой коллекции.

Условия используются для вывода статуса средства и активного пункта навигации:

```django
{% if needs_attention %}
    Требует внимания
{% else %}
    В порядке
{% endif %}
```

## 7. Фильтры шаблонов

## 10. База данных, миграции и Django ORM

В ПР9 выбрана стратегия создания отдельной базы, управляемой Django, с переносом
данных из базы ПР7:

- `data/cosmetic_inventory.sqlite` - исходная база ПР7, открываемая скриптами
  переноса только для чтения;
- `db.sqlite3` - целевая локальная база Django, исключённая из Git;
- `products/migrations/0001_initial.py` - начальная миграция моделей;
- миграции `0002`-`0004` добавляют вычисляемое поле `low_stock`, заполняют
  читаемые `slug` и затем закрепляют их уникальность;
- миграция `0005_product_image.py` добавляет необязательное поле изображения.

Скрипт `db/inspect_source_db.py` выводит таблицы, столбцы, ключи и количество
записей исходной базы без её изменения. Скрипт `db/import_sqlite_to_orm.py`:

1. Проверяет наличие таблиц, корректность дат, количества и внешних ссылок.
2. Переносит бренды, категории и затем средства.
3. Сохраняет исходные идентификаторы и связи.
4. Выполняет запись внутри `transaction.atomic()`.
5. Использует `update_or_create()`, поэтому допускает повторный запуск без
   дублирования данных.

Представления используют ORM-операции:

- `get()` и `get_object_or_404()` для получения одной записи;
- `filter()`, `exclude()` и объекты `Q` для фильтрации и поиска;
- `order_by()` для сортировки;
- `select_related()` для загрузки бренда и категории;
- `values()` и `values_list()` для сокращённых выборок;
- `aggregate()` с `Count`, `Sum`, `Avg`, `Min` и `Max`;
- `annotate()` для статистики по брендам и категориям;
- `create()`, `update()` и `delete()` для CRUD-операций;
- `Paginator` для постраничного вывода.

Пользовательский `ProductQuerySet` объединяет повторяемые операции поиска,
фильтрации, загрузки связей и отбора позиций, требующих внимания. Общий
контекстный процессор передаёт в шаблоны название сайта и количество средств.

### Диагностика SQL-запросов

Django Debug Toolbar подключена для локальной разработки. Панель отображается
только при `DEBUG = True` и запросе с адреса из `INTERNAL_IPS`. Раздел SQL
позволяет проверить количество и текст запросов. Каталог выполняет четыре
запроса; бренд и категория загружаются через `select_related()`, поэтому
количество запросов не растёт для каждой карточки товара.

Файлы ПР7 `sql/schema.sql`, `sql/queries.sql`, `db/database.py`,
`db/import_json.py` и `db/queries.py` сохранены как предыдущая реализация и
продолжают проверяться тестами. Веб-представления больше не используют прямые
SQL-запросы или `sqlite3`.

## 11. Основные модули

### `models/products.py`

Содержит сохранённую модель предметной области консольной версии и операции над
обычными коллекциями Python.

### `products/models.py`

Содержит ORM-модели `Brand`, `Category` и `Product`, пользовательские
`ProductQuerySet` и менеджер, поля, связи, ограничения, читаемые URL и методы
предметной области.

### `products/admin.py`

Настраивает административный интерфейс моделей инвентаря, поиск, фильтры,
встроенные списки связанных средств и групповое пополнение запасов.

### `products/context_processors.py`

Добавляет общие данные сайта и количество средств в контекст всех шаблонов.

### `products/forms.py`

Содержит `ProductFilterForm` на основе `forms.Form` и `ProductForm` на основе
`forms.ModelForm`, настройки виджетов и серверную валидацию даты и изображения.

### `storage.py`

Отвечает за предыдущую реализацию загрузки и сохранения данных в формате JSON.

### `db/database.py`

Создаёт и настраивает соединение с отдельной SQLite-базой проекта.

### `db/import_json.py`

Переносит исходные данные из JSON в таблицы `brands`, `categories` и
`products`.

### `db/queries.py`

Содержит функции параметризованного выполнения запросов списка, поиска,
фильтрации и статистики из сохранённого SQL-слоя ПР7.

### `db/inspect_source_db.py`

Исследует структуру и количество записей исходной базы ПР7 в режиме только для
чтения.

### `db/import_sqlite_to_orm.py`

Переносит данные из базы ПР7 в таблицы, управляемые Django ORM.

### `homepage/views.py`

Содержит представление главной страницы и общий обработчик ошибки 404.

### `products/views.py`

Получает данные через Django ORM и содержит представления списка, подробной
страницы, поиска, фильтрации, сортировки, пагинации, списка внимания,
статистики, создания, редактирования и удаления средств.

### `main.py`

Содержит сохранённую консольную версию приложения.

### `utils.py`

Содержит вспомогательные функции безопасного консольного ввода.

## 12. Установка и запуск

Клонировать репозиторий и перейти в каталог проекта:

```bash
git clone https://github.com/kkapanny/cosmetic_inventory_system.git
cd cosmetic_inventory_system
```

Создать и активировать виртуальное окружение:

```bash
python -m venv .venv
source .venv/bin/activate
```

В Windows команда активации имеет вид:

```text
.venv\Scripts\activate
```

Установить зависимости:

```bash
python -m pip install -r requirements.txt
```

Проверить исходную базу ПР7:

```bash
python db/inspect_source_db.py
```

Создать структуру целевой базы Django:

```bash
python manage.py migrate
```

Перенести данные ПР7 в ORM-базу:

```bash
python db/import_sqlite_to_orm.py
```

Импорт можно запускать повторно: записи с теми же идентификаторами обновляются,
а дубликаты не создаются.

Проверить конфигурацию:

```bash
python manage.py check
python manage.py makemigrations --check
python manage.py showmigrations
```

Запустить веб-сервер:

```bash
python manage.py runserver
```

После запуска веб-интерфейс доступен по адресу:

```text
http://127.0.0.1:8000/
```

Для ручной проверки административного интерфейса создать суперпользователя и
открыть страницу входа:

```bash
python manage.py createsuperuser
```

```text
http://127.0.0.1:8000/admin/
```

На локальных HTML-страницах при `DEBUG = True` также отображается Django Debug
Toolbar с разделом SQL.

Консольная версия запускается отдельно:

```bash
python main.py
```

- `test_orm_queries.py` проверяет CRUD, связанные выборки, фильтрацию,
  сортировку, `exclude()`, `values()`, агрегирование и аннотирование;

- `test_forms.py` проверяет формы фильтрации и средства, доступные поля,
  виджеты, валидацию даты, формата и размера изображения;
- `test_web.py` проверяет получение данных через ORM, шаблоны, контекст,
  маршруты, поиск, пагинацию, статистику, создание, редактирование, удаление,
  CSRF-защиту, загрузку изображений, количество запросов и обработку ошибок
  404;
